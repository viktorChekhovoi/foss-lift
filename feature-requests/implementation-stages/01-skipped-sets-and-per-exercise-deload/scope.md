# Stage 01 — skipped-sets-and-per-exercise-deload

Source: `feature-requests/skipped-sets-and-timed-deload.md`

## Why this is one stage

The request has two halves — a skipped set stops being a performance failure, and the timed (layoff) deload starts tracking inactivity per exercise instead of per workout — and they are joined by the word "instead". Landing only the first would make skipping strictly free: an exercise nobody trains would hold its targets forever with nothing left to catch it, which is worse than today's behaviour, not better. Landing only the second is coherent but delivers none of the request. There is no ordering between them in code either: the verdict change lives in `ExerciseEntry`/`advanceProgression`, the inactivity change lives in `layoffFor`/`applyLayoffDeload`, and neither reads the other. The two halves share their tests, their catalogue entries and their user-visible copy, so splitting them would duplicate all three and produce a first stage nobody should ship.

Estimated at 18–21 senior developer days, which fits the 10–25 day target for a single stage, including persisted offer handling, first-training eligibility and upgrade coverage.

## Planning proposal awaiting user confirmation: hold clean partial exercises

The feature request asks the user to choose whether partial exercises are judged on performed sets alone or hold until complete. The preceding review scope selected Option B; no user confirmation is present in the supplied conversation or decision record. Option B below is therefore the prior review's proposal, not a confirmed user decision. The user has been asked to choose during this planning revision. Record their answer here before completing planning, then carry it into the catalogue before dependent tests or implementation.

**Proposal — Option B, awaiting the user.** A performed working set that falls short is still a miss and follows existing performance rules, even if other sets were skipped. Otherwise, if any planned working set was skipped, the exercise neither succeeds nor fails: all normal targets and both streaks hold. With no performed sets it also holds. Only completing every planned set without a shortfall earns a success.

The hold includes adopting a heavier performed load and establishing a previously absent weight target: neither happens in a clean partial exercise. A partial exercise with a recorded shortfall follows the existing miss path, including its existing target-adoption rules. Any performed working set resets inactivity regardless of this progression verdict.

**Alternative — Option A, also awaiting the user's choice.** Judging only performed sets would allow two clean sets out of three to earn a success. Option B requires the complete prescription for success, while preserving the request's rule that a recorded shortfall remains a performance miss.

All clean-partial clauses below, including target adoption, legacy bar correction, recap copy, catalogue rewrites and the partial cases in criteria 3, 17 and 19, describe the Option B proposal conditionally. They are not approved acceptance criteria until the user answers. If the user chooses Option A, revise these dependent clauses during planning before writing the catalogue; do not leave that reconciliation to implementation. Fully skipped exercises, recorded shortfalls and per-exercise inactivity do not depend on this choice.

The outcome becomes three-valued (success / miss / neither). Keep the existing two-valued `SessionVerdict` used by cycle and GZCL rules; represent the neutral outcome with a nullable verdict or a wider type that is resolved before calling `stepProgression`. This is an internal representation choice, not an unresolved behaviour.

## Scope

All new progression, recap and per-exercise layoff rules below apply only to ordinary Weight, Reps and Weight + Reps slots: counted weight/reps modes without a cycle, GZCL tier or RPE target. Time (`ProgressionMode.time`), cycle, GZCL and RPE progression remain outside this request. Use this same eligibility boundary for Finish and Start so a shared verdict or offer helper cannot change an excluded mode accidentally.

### Progression: a skipped set is not a miss

`ExerciseEntry.succeeded` currently reads `sets.every((s) => s.done && !s.missedGoal)`, so an unlogged set is a miss with no way to tell it from a set that came up short. Replace it with the three-valued outcome above. A fully skipped or clean partial exercise moves nothing: no step, no back-off, no streak change, no write to the slot at all during progression on Finish.

`finish()` in `lib/state/active_workout.dart` passes the outcome to `AppDatabase.advanceProgression`. Make the null case explicit in that signature rather than filtering it out in the caller, because the decision is not the same for every slot:

- Ordinary weight, reps and Advanced (weight + reps) slots take the new rule. This is the scope of the request.
- Time slots (`it.progression == ProgressionMode.time`), cycle slots (`it.runsCycle`) and GZCL slots (`it.gzclTier != null`) keep today's verdict and progression paths. Their verdict still requires every planned set to be logged without a shortfall; a fully skipped or clean partial exercise remains a miss. If the shared outcome is nullable, convert neutral to `SessionVerdict.miss` before their existing dispatch. A skipped plank can therefore still increase its failure streak or reduce `holdSeconds` at the existing threshold. Cycle weeks, GZCL ladders and the GZCL T3 final-AMRAP trigger remain unchanged. RPE slots retain the existing `finish()` bypass of automatic progression.

Three existing rules need re-checking against the new outcome, and each needs a test:

- **Loading the bar past the suggestion is itself progression** (`05.loading-bar-past-suggestion-itself`). The neutral outcome takes precedence over this rule: a clean partial exercise holds its stored weight even when every performed set exceeds it. For example, one clean 85 kg set out of three planned at 80 kg leaves the target at 80 kg and both streaks unchanged. Fully completed exercises and partial exercises with a recorded shortfall retain existing target-adoption rules, including exclusions for percentage-based prescriptions.
- **A weight slot with no suggested weight takes one from the session** (`05.weight-mode-slot-no-suggested`). `ExerciseEntry.sessionLoadKg` falls back to `workingKg` when nothing was logged. A weight typed onto the board must establish no target when the exercise is fully skipped or clean but partial; the stored target remains null. Once all sets are performed, or a performed set has a shortfall, existing target-establishment and performance rules apply.
- **A target is never stored below its own bar** (`05.target-never-stored-below-its-bar`). Target preservation takes precedence on a neutral Finish: deliberately defer the legacy correction when the exercise is fully skipped or clean but partial. A stored 15 kg target under a 20 kg bar stays 15 kg in storage in those cases. Keep the live board's existing load floor; this decision does not prescribe lifting below the bar. The next non-neutral progression outcome uses the existing read/write correction and bar baseline, and an explicitly accepted layoff still applies its existing floor. Edit the catalogue entry to state this timing exception rather than retaining its blanket correction claim. Neutral Finish must not report the deferred correction as progression.

### Timed deload: inactivity per exercise

`layoffFor(workoutId)` reads `lastTrainedAt(workoutId)`, which is the start time of the most recent finished session filed against that workout. Completing any part of a workout therefore resets the clock for every exercise in it, which is the behaviour the request removes.

The last-trained query needs no new history columns. `finish()` already writes a `SessionSets` row only for a set that was logged, so "this exercise was performed in this session" is already recorded, for every session in every shipped install. Query `sessionSets` joined to finished `sessions`, matched on `exerciseId`, and select the latest session by `startedAt`, then `id` to break ties. Its start time measures the gap; its identity distinguishes successive training sessions for offer handling. This uses the same history as `lastLoggedWeight` and the existing `session_sets_exercise_session_set` index. Existing history remains readable; sets whose `exerciseId` is null do not match.

Tracking by exercise rather than by workout slot is the reading to take: the request says "since that exercise was last trained", and a lift that appears in both Push A and Push B has been trained when either of them trained it. Note it in the catalogue entry, because it is a real choice and the alternative is defensible.

**Decision: a new slot must establish training before it can receive a layoff offer.** A newly built, copied, library-added or routine-code-imported slot starts ineligible, even when its exercise has old global history. It becomes eligible when a subsequent Finish saves at least one performed working set for that exercise, in any workout. Until then, starting or finishing workouts with that exercise entirely skipped leaves the slot ineligible and its freshly entered target untouched by timed deloads. Thus an 80 kg bench added today is not offered a cut from a session 200 days ago, whether the new slot belongs to a new Push workout or an already trained one. After training is established, use the latest global performed session for its clock as above; training in Push A then keeps an existing eligible Push B bench current.

Persist this eligibility as a per-slot boolean, default false for genuinely new slots. In the same transaction that saves a finished session and its sets, establish eligibility for existing in-scope slots whose exercise has a performed working set in that save. Do not infer first-training eligibility by scanning old global history on Start. An unfinished, discarded or fully skipped session cannot establish it, and warm-ups remain outside the persisted working-set history. Carry the flag through `ItemDraft`, replacement writes, reordering and unrelated slot edits; deleting and recreating a slot, or replacing its exercise identity, starts it false. A duplicate made as a new slot starts false even if the original is eligible. Full backups retain the flag; routine codes do not carry it.

For shipped slots, the additive migration initializes eligibility only when a finished session filed against that slot's workout contains a performed set with that exercise id. Global history from another or deleted workout cannot establish a legacy slot's eligibility. Existing history has no slot creation time or slot id, so this workout-plus-exercise match is the explicit compatibility fallback for migrated rows; do not claim it proves when a particular duplicate slot was first trained. A migrated slot without that evidence starts false and follows the subsequent-Finish rule. Do not change historical rows or targets. This preserves layoff eligibility for previously trained prescriptions while keeping never-trained workouts free of offers on their first Start.

For excluded Time, cycle, GZCL and RPE slots, retain the existing workout-based layoff clock, offer eligibility and decline behaviour. A mixed workout can therefore contain in-scope offers computed from exercise history and excluded-slot offers computed from workout history. Combine them in the existing single accept/decline dialog, identify each affected slot and apply only its applicable percentage. Per-exercise acknowledgement belongs only to in-scope slots; it must neither suppress nor apply an excluded slot's offer. A finished workout continues to reset the excluded slots' workout-based gap even when those slots are skipped.

For in-scope slots, the workout-wide offer becomes a set of per-exercise ones:

- `layoffFor` gains a per-workout form that returns one offer per eligible slot, carrying its `LayoffDeload`, slot id, exercise identity and name, last-performed session identity, uncapped elapsed period and proposed target. Require the first-training eligibility flag as well as matching global history: neither a never-performed exercise nor a new slot with only older history receives an offer. Reading an offer writes nothing.
- Accepting applies each displayed slot's proposed target and clears its streaks; declining leaves targets and streaks unchanged. Both explicit choices handle the current period as described below. Dismissing the dialog writes nothing. Keep the movement count honest: a bodyweight slot with no target moves nothing, but an explicit response still handles its displayed period.
- The existing threshold, per-period percentage, period cap, cut cap, rounding and floors are unchanged. Each eligible offer uses the existing arithmetic for its total reduction, while the separate response state controls when it can be offered again.

**Decision: an explicit response suppresses only the current inactivity period for each in-scope slot.** Compute the uncapped elapsed period as `gapDays ~/ thresholdDays` when deloads are enabled. Accepting or explicitly declining handles that period; another Start in the same period does not repeat the offer. The next whole period makes an offer available again, even if the exercise is still skipped. Dismissal by back-tap or tapping outside the dialog is not a response: it writes nothing and leaves the offer available on the next Start. Keep the existing accept/decline controls and their effects on targets and streaks; replace only the in-scope stateless response handling in `06.declining-not-recorded`. Neither a response nor a dismissal changes the real last-trained time.

Do not use `LayoffDeload.periods` as the response key: it is capped at three and would permanently suppress offers after the third response. The uncapped period keeps advancing at days 56, 70 and beyond while `layoffDeload` continues to cap the reduction at its existing limits. Persist the handled gap's training timestamp/session id, uncapped period, threshold used and next period boundary as nullable state on `WorkoutItems`. A newer performed session starts a new gap; merely falling back to older history after deletion must not erase the existing response or reduction baseline. Reopening the app, discarding the session or changing deload settings does not erase this state. A settings change keeps the already recorded next boundary; when that date arrives, evaluate the current settings and, on a response, record their next boundary. Disabling deloads produces no offer.

**Repeated accepts must not compound the reduction across periods.** On the first acceptance in a gap, retain the slot's pre-cut target as its reduction baseline. Calculate later proposals with `deloadedTarget` from that same baseline and the current capped total percentage, never from an already reduced target. For an 80 kg baseline, accepting at 14, 28 and 42 days yields 72, 64 and 56 kg; accepting in any later period cannot cut it below 56 kg with unchanged default settings. A previous decline establishes no baseline and applies no cut. A later proposal must not increase the current target if settings become less severe. Preserve the existing rep-range width and bar/mode floors, and treat a null weight target as having nothing to cut. At the cap a later-period offer can propose retaining the already reduced target; report zero movement rather than claiming a further cut.

Store each explicit response, the baseline on acceptance and any accepted target/streak changes in one transaction, scoped to the displayed slot, exercise and training identities. Reapplying the same offer is a no-op, and a stale offer whose target, axis or training identity changed must be recomputed before it can be accepted. Different slots for the same exercise share the training clock but keep independent response state and baselines. Preserve both through edits that only reorder or rename a slot. An explicit edit of its target or progression axis invalidates its old reduction baseline, but does not erase period suppression or count as training; the next eligible acceptance takes the edited target as its new baseline. A newer performed session also ends the old baseline, so the next layoff starts from the then-current target.

Apply that invalidation to both slot-edit paths: the workout builder's `ItemDraft` → `replaceWorkoutItems` replacement and the live board's `_editSlot` → `itemUpdate` → `AppDatabase.updateWorkoutItem` in-place update. The latter currently writes only companion fields that are present, so omitting the baseline would retain stale state. Compare the effective persisted target/axis before and after the edit and clear the baseline atomically with an actual change; opening and saving unchanged settings or editing only rest must preserve it. Share the invalidation rule across both paths. This concerns saved slot settings; the live working-weight control alone does not edit the stored prescription.

This requires a schema increment and a new additive `onUpgrade` rung (currently version 18 → 19; use the next version at implementation time). Existing rows start with null response state and reduction baseline, and initialize first-training eligibility from the workout-plus-exercise history rule above; the old build recorded no decisions, so do not fabricate responses or rewrite historical targets. Preserve this state through `ItemDraft` and `replaceWorkoutItems` under the edit rules above, even though that path replaces row ids. New slots and routine-code imports start ineligible with null response state and baseline; none of that state travels in routine share codes. Full database backups carry all three; old backups use the same migration. Regenerate `database.g.dart` with build_runner, keep shipped migration rungs and wire formats intact, and update the table map in `ARCHITECTURE.md`.

### Session start, notice and recap

Keep one dialog with one accept and one decline, and name the exercises, current targets and proposed targets. Show the total percentage against the retained baseline when there was an earlier cut: 64 kg after an earlier 72 kg target is a total 20% reduction from 80 kg, not a fresh 20% reduction from 72 kg. A proposal already at its capped target must not promise another reduction. `startWorkoutLayoffBody` currently says "reduce every target in this workout by {percent}%", which stops being true; rewrite it. Preserve dismissal as distinct from an explicit decline through the dialog's nullable result.

Constrain the Start dialog to the available viewport and make its exercise list scrollable, with both actions reachable when the list exceeds the available height. Exercise names and target labels must wrap without clipping. Include this dialog explicitly in the text-size and locale sweeps: the existing screen sweep does not open it. Test ten or more eligible slots with differing cuts and long exercise names at 1.0×, 1.3× and 2.0× text on a 360 × 780 dp viewport in all five locales.

`LayoffNotice` is `({int percent, int days})` and is carried into the session and shown for its length. Apply the dialog's distinction between the total baseline reduction and the actual target change to the notice too; zero movement must not claim a new cut. If the notice grows to describe several exercises, `_readNotice` in `lib/state/session_snapshot.dart` must keep reading the old two-key map: that snapshot is on disk on shipped phones, and its reader casts with `as int` today, so a shape change without a compatibility path throws on the first resumed session after the update. **Recap decision: omit fully skipped in-scope exercises from the progression report.** `finish()` must not append a `ProgressionOutcome` for them or read the slot back solely to construct that recap row. A clean partial in-scope exercise with a stored target does get a neutral held row, with a localized reason that the planned sets were not all performed. Do not derive its note from preserved success/failure streaks or imply this session earned either outcome. A clean partial weight exercise without a stored target remains omitted under the existing targetless-row rule. `04.finish-asks-when-sets-are-unlogged` describes the confirmation dialog as reporting sets that "count as misses for progression". That blanket statement becomes false. Keep the dialog counting unlogged working sets, but remove the universal miss claim from its copy. The catalogue must distinguish the new rules for Weight, Reps and Weight + Reps from unchanged excluded modes.

The deload settings explanation in `lib/screens/exercise_settings_screen.dart` also changes. Rewrite `settingsDeloadOnNote` and `settingsDeloadOffNote` in every locale. Enabled copy must describe the per-exercise training gap for Weight, Reps and Weight + Reps, the configured threshold/percentage and existing cap, and renewed offers after another whole period following an explicit response. It must not imply that training another exercise resets that gap or that later offers compound reductions. Keep the excluded modes' workout-based rule clear where the explanation refers to them. Disabled copy must say timed-deload offers are off, without suggesting that ordinary performance progression is disabled or that inactivity is measured only per workout. Retain the current controls and settings values; adjust placeholders and their caller together if needed.

New and changed strings go in `lib/l10n/short/` or `lib/l10n/long/` by the three-word rule in `lib/l10n/README.md`, for all five locales (en, es, pt, pt_BR, uk), then `dart run tool/l10n.dart` and `flutter gen-l10n`.

## Acceptance criteria

Each row of the acceptance table in the feature request is an integration test, written from the catalogue entries and seen to fail before the code exists. Unless explicitly testing excluded-mode compatibility, these criteria apply to Weight, Reps and Weight + Reps only.
